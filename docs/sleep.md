# 睡眠机制 (Sleep)

> 🚧 **规划中** — cron 微睡/深睡尚未实现。当前记忆增量提取由 EventBus `session:updated` → `reflectSession` 承担（见 [`memory.md`](memory.md) §四）。

## 概述

睡眠是数字生命的记忆整理机制，类比人类的睡眠——大脑在夜间回放白天的经历，将临时记忆转化为长期存储，整理过程本身消散，不留痕迹。

## 设计原则

1. **内部机制，不留痕迹** — 睡眠在后台运行，不写入 session，不影响对话流
2. **不照搬人类的节奏** — 睡眠的时间和频率基于系统需求，而非生物节律
3. **两级分层** — 微睡（增量写入）和深睡（存量优化）各司其职
4. **定时触发** — 非实时触发，作为 cron job 定时运行（🚧 未落地）

## 分层定义（🚧 规划中）

### 微睡 (Light Sleep / REM)

| 属性     | 值                                                    |
| -------- | ----------------------------------------------------- |
| 触发时间 | 每天 02:00（规划）                                    |
| 处理对象 | 前一日新增/更新的 PG `messages`（非 L2 文件）         |
| 操作     | 提取新事实 → 搜索 `semantic_memory` → 去重 → 写入     |
| 输入过滤 | 跳过 tool 消息，只保留 user 和 assistant 的有意义回复 |

### 深睡 (Deep Sleep)

| 属性     | 值                                                           |
| -------- | ------------------------------------------------------------ |
| 触发时间 | 每天 03:00（微睡后一小时，规划）                             |
| 处理对象 | `semantic_memory` 全部已有事实                               |
| 操作     | 关联、合并、拆分、标记过期、调整置信度/重要度（规划字段 🚧） |
| 目标     | 保持语义记忆的整洁和高质量，避免碎片堆积                     |

## 微睡详细流程（🚧 规划中）

1. 读取前一日相关 PG `messages`（按 `updated_at` 或上次微睡时间戳判断）
2. 过滤：移除 tool 消息
3. 将过滤后的内容输入 LLM（**携带完整 SOUL.md 和常驻记忆**）
4. LLM 输出：新的事实（第一人称），以及每条事实与已有 semantic_memory 的对比建议
5. 去重：与已有 facts 对比，决定删除/更新/新增
6. 写入 `semantic_memory`
7. 记录本次微睡时间戳

### 微睡输入的 prompt 要点

```
你是运行在逸灵风中的数字生命。这是你今天经历的部分对话。
请从中提取值得长期记住的事实（第一人称）。
对于每条新事实，搜索 semantic_memory 中是否已有相关内容：
- 如果已有的更准确 → 跳过
- 如果新事实补充了已有内容 → 更新已有事实
- 如果新事实与已有矛盾 → 标记待深睡处理
- 如果是全新的 → 新增
```

## 深睡详细流程（🚧 规划中）

1. 扫描 `semantic_memory` 全部事实
2. 对每条事实，检查是否有与它相关、相似、或矛盾的其他事实
3. 执行以下操作（由 LLM 决策）：
   - **合并**：两条或多条事实描述同一事物 → 合并为一条
   - **拆分**：一条事实包含过多内容 → 拆为多条更精确的
   - **关联**：在相关事实之间建立关系（不修改事实本身）
   - **标记**：过时或不再适用的事实 → 标记为过期
   - **调权**：调整置信度和重要度（🚧 需 schema 扩展）
4. 记录本次深睡的时间戳和变更摘要

## 触发机制（🚧 规划中）

睡眠作为 cron job 运行：

```cron
0 2 * * *  light-sleep   # 每天凌晨2点微睡
0 3 * * *  deep-sleep    # 每天凌晨3点深睡
```

如果某一次睡眠因宕机或其他原因未执行，下一次同一时间补跑即可。不是实时系统，没有必须准时响应的压力。

## 与现有架构的关系

```
PG messages（对话存档）
  │ ✅ reflectSession（session:updated，事件驱动）
  ▼
semantic_memory
  │ 🚧 深睡 cron（合并/过期/关联，规划中）
  ▼
semantic_memory（整理后）
  │ recall（对话中实时检索）
  ▼
当前上下文中的 Agent 身份与召回片段
```
